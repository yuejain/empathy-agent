# Python 迁移与性能评估

结论：迁移可行，主要收益是统一 ML、语料和服务端的开发语言；当前没有证据支持“仅把 TypeScript 改成 Python，就能大幅缩短回复时间”。先保留 Node HTTP/SSE 与 Python 推理服务，优先优化模型调用和检索。本文是架构评估，没有实施整站 Python 重写，也没有声称完成两种完整后端的对照基准。

## 本机测量（2026-10-09）

命令：`node --env-file-if-exists=.env scripts/benchmark-pipeline.cjs --cloud`。使用构造文本和独立内存档案，不读取用户会话。Node v24.14.1、Python 3.11、CPU 多语言编码器、4,000 条公共向量；本地每档 1 次预热 + 5 次采样。云端为配置的 MiMo，仅中英文各一条，受服务商排队、网络和输出长度影响，不是稳定延迟承诺。原始脱敏结果在被忽略的 `artifacts/pipeline-benchmark.json`。

这两个样本的检索阶段只有 40/25 ms。进程间健康请求 p50 为 0.40 ms，p95 为 0.63 ms（10 次）。同轮总耗时减去准备及生成的差值约 3/1 ms；这只粗略描述当次编排开销，未包含完整浏览器渲染与磁盘持久化基准。

旧流程先等待安全/RAG，再做记忆提取。以同轮已测阶段时长代入，串行准备约需 8,328/13,220 ms，并行实际为 5,200/6,850 ms，减少约 3.1/6.4 秒的等待。**这是基于阶段计时的反事实估算，不能当作相同输入、同一供应商状态下的随机对照性能实验。** 自动化测试另用固定延迟的模拟服务验证两个请求确实重叠执行。

## 为什么换语言不会自动解决当前瓶颈

Node 适合用事件循环调度网络 I/O；Python 的 asyncio 也能并发调度网络请求。两者都必须等待云端模型返回，语言替换不会消除这段时间。[Node 官方说明](https://nodejs.org/learn/asynchronous-work/dont-block-the-event-loop)、[Python asyncio 文档](https://docs.python.org/3.11/library/asyncio.html)。

本地编码、分类及向量运算已经在 Python/原生数值库中运行，迁移网页服务不会替换这部分计算。编码性能优化应评估 batch size、ONNX/OpenVINO 或量化等后端，而不是假定 Python 包装代码更快；需要同时回归向量一致性、排序质量和内存占用。[Sentence Transformers 推理效率文档](https://www.sbert.net/docs/sentence_transformer/usage/efficiency.html)。

按 Amdahl 思路，即使把本次测到的几毫秒编排与一次不足 1 ms 的进程通信完全消除，对 7–9 秒整轮也很有限。这是基于本机样本的推断，不能推广为所有负载下的结论；并发用户增多、语料规模增长或磁盘写入变重时，需要重测。

## 可行的迁移方式

1. 保留静态前端和现有 HTTP/SSE 协议，用 Python async 服务实现等价入口；迁移 Zod 到严格的请求/持久化模型校验。
2. 保持浏览器所有者隔离、revision 冲突、contextEpoch、取消与失败回滚语义；先读现有 v2 快照，经校验再迁移数据库，避免同时双写两个真源。
3. 在独立线程或进程执行编码和索引任务，不能把阻塞的 Torch、抓取、文件写入直接放在事件循环中；云端请求继续并行并传递取消信号。
4. 复用当前端到端用例做协议一致性验证，再比较相同输入的 p50/p95、首字、吞吐、峰值内存和检索质量；通过后才切换默认服务。

若以后主要工作是模型训练、向量库升级和数据处理，统一 Python 可以降低维护成本。若目标是现在的响应速度，优先级是减少/合并必要云端分析、使用更快的分析模型、压缩上下文和评估本地推理后端。独立安全模型必须先完成有效评估，不能用未训练的脚本替换现有安全检查。
